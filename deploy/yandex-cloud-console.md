# Инструкции для расширения Claude для Chrome — консоль Yandex Cloud

Браузерная часть развёртывания. Всё, что делается по SSH (nginx, сертификат,
заливка файлов), сюда не входит — расширение работает только с консолью.

Порядок такой:

1. **Этап 1** — создать виртуальную машину. Промпт ниже. ✅ сделано
2. **Этап 2** — настроить сервер по SSH и залить сайт. Это терминал,
   см. `deploy/DEPLOY.md`. ✅ сделано
3. **Этап 3** — сузить доступ по SSH. Промпт ниже. Не срочно: вход и так
   только по ключу.
4. **Этап 4** — подключить CDN для зарубежных посетителей. Промпт ниже, но
   сперва там решается вопрос с DNS, который в консоли не решается.

Параметры машины взяты из замеров: сайт занимает 98 МБ, страница весит около
0,9 МБ, процессор при раздаче статики простаивает.

## Этап 3. Сузить доступ по SSH

Соответствует шагу 7 из `DEPLOY.md`. Порт 22 сейчас открыт всему интернету.
Вход и так только по ключу, паролей нет, поэтому шаг не срочный — но и
откладывать незачем.

**Сначала узнайте свой адрес** на той машине, с которой ходите по SSH:

```bash
curl -s ifconfig.me
```

Именно свой, а не адрес какого-нибудь агента: у агента, работающего через VPN,
это будет адрес выхода VPN, и правило пустит кого угодно из этой сети, а вас —
нет.

Два предупреждения, которые стоит прочесть до, а не после.

**Адрес может быть динамическим.** У домашнего интернета он обычно меняется —
после смены вы просто не войдёте по SSH. Проверить просто: выполните команду
сегодня и завтра. Если адрес разный — вписывайте подсеть провайдера или оставьте
как есть.

**Заблокировать себя навсегда нельзя.** Группа безопасности правится из веб-консоли,
а она доступна из браузера и без SSH. Даже если ошибётесь в адресе — вернётесь в
консоль и поправите правило. Сайт при этом продолжит работать: он живёт на портах
80 и 443, их мы не трогаем.

```
Ты работаешь в консоли Yandex Cloud в моём реальном аккаунте. Задача —
сузить одно правило в группе безопасности, чтобы порт SSH был доступен не
всему интернету, а только с моего адреса.

ЖЁСТКИЕ ОГРАНИЧЕНИЯ, соблюдай буквально:
- Меняй ТОЛЬКО правило для порта 22 (SSH) в группе безопасности
  kabanov-agency-web-sg.
- НЕ ТРОГАЙ правила для портов 80 и 443 — на них работает сайт, и их

- НЕ ТРОГАЙ правила исходящего трафика.

- Не создавай сервисные аккаунты, не выпускай ключи, не меняй IAM и

ШАГ 1 — снять текущее состояние, ничего не меняя.

Если интерфейс не даёт отредактировать источник у существующего правила, а
```

## Этап 4. CDN для зарубежных посетителей

Сервер стоит в России. Для посетителей из РФ это правильно, но из-за рубежа
каждый запрос идёт через полмира. CDN держит копии файлов ближе к посетителю —
сайт у нас статический, кэшируется целиком, так что выигрыш будет заметным.

### Что выяснила разведка (проверено в консоли и документации)

| Вопрос | Ответ |
|---|---|
| Тип DNS-записи | **только CNAME** на балансировщик вида `e1b83ae3….topology.gslb.yccdn.ru` |
| Корень домена | **нельзя**, и обход через ALIAS/ANAME Yandex прямо не рекомендует |
| Сертификат в Certificate Manager | **нет ни одного**; тот, что на сервере, для CDN не годится |
| Стоимость при 20 ГБ/мес | **150 ₽** — пакет 150 ГБ, трафик целиком внутри пакета |

Про корень домена важно понять причину, иначе легко выбрать неправильный обход.
CNAME по RFC не сосуществует с другими записями для того же имени, а на вершине
зоны обязаны быть SOA и NS — плюс у нас там MX почты Google Workspace. Запись
ALIAS это ограничение обходит технически, и Yandex Cloud DNS её поддерживает,
но для CDN документация запрещает:

> «Cloud CDN следует использовать только с ресурсными записями CNAME, поскольку
> при использовании записи ANAME конечный пользователь получит ответ, не зависящий
> от его геолокации.»

То есть перенос DNS в Yandex не решает задачу, а лишь даёт сделать неправильно:
CDN раздаёт с ближайшей к посетителю точки именно потому, что отвечает на CNAME
по геолокации, а ANAME эту логику ломает — все получают один сервер.

Официальная рекомендация Yandex — разделить домены: CDN на поддомене, почта и
лёгкий контент на апексе.

### Что это значит для нас

Единственный архитектурно чистый путь — **перевести сайт на `www.kabanov.agency`,
а апекс оставить редиректом на него**. Тогда весь пользовательский трафик идёт
через CDN, а MX-записи остаются на апексе нетронутыми.

Это не настройка на вечер. Сейчас канонизация устроена наоборот: `www` отдаёт
301 на апекс, а во всех 83 страницах `canonical`, `og:url` и `hreflang` указывают
на апекс. Переезд на `www` требует:

1. Развернуть редирект в `deploy/locations.conf`: апекс → `www`, а не наоборот.
2. Переписать в 83 страницах `canonical`, `og:url` и три `hreflang` — иначе
   поисковики получат канонический адрес, который сам себя перенаправляет.
   Делается отдельным идемпотентным шагом, как `fixes` и `debrand`.
3. Обновить `sitemap.xml`.
4. Выпустить сертификат для `www.kabanov.agency` в Certificate Manager. Требует
   подтверждения владения доменом записью в DNS у GoDaddy.
5. Прописать CNAME для `www` на балансировщик CDN.
6. Прогнать `check:seo`, `check:nginx`, `audit` и `check:nav` по новому адресу.

Откат на любом шаге — вернуть CNAME `www` в A-запись на `158.160.179.74`.

### Стоит ли вообще

Ответ зависит от того, сколько у сайта зарубежных посетителей, а этого мы пока
не знаем. Google Analytics поставлен и уже собирает географию — через две-три
недели в отчёте «Пользователи по странам» будет видно, идёт ли речь о заметной
доле или о единицах визитов.

Пока данных нет, разумнее не платить 150 ₽ в месяц и не затевать переезд на
`www` ради предположения. Сайт статический, сжатие включено, из-за рубежа он
открывается — просто медленнее, чем мог бы.

### Что важно не перепутать при настройке

**Протокол до источника — только HTTPS.** Наш nginx безусловно перенаправляет
HTTP на HTTPS. Если CDN пойдёт к источнику по HTTP, он получит редирект и либо
зациклится, либо закэширует его вместо страницы. Сертификат на сервере есть,
Let's Encrypt, автопродление настроено.

**Сжатие на стороне CDN включать нельзя.** Файлы уже сжаты заранее, а данные CMS
(расширение `.cmsdata`) при сжатии ломают загрузчик: он сверяет длину ответа с
ожидаемой и выключает интерактивность страницы. Мы на этом уже обжигались.

**Время жизни кэша брать из заголовков источника.** Файлы в `/assets` помечены
`immutable` на год, HTML — `must-revalidate`. Если CDN переопределит это своим
значением, после обновления сайта посетители будут неделю видеть старую версию.

### После подключения

Пока DNS не переключен, CDN можно проверить в обход — и это стоит сделать
до переключения, а не после:

```bash
curl -sI -H 'Host: kabanov.agency' https://<адрес-выданный-CDN>/ | head -20
```

Проверять надо три вещи:

```bash
# 1. Данные CMS не сжимаются — иначе сайт потеряет интерактивность
curl -sI -H 'Accept-Encoding: gzip, br' https://kabanov.agency/assets/cms/.../*.cmsdata

# 2. Модули отдаются как javascript — иначе страницы не оживут
curl -sI https://kabanov.agency/assets/js/app.KNQD3WMr.mjs | grep -i content-type
```

## Почему именно такие параметры

| Параметр | Значение | Почему |
|---|---|---|
| Ubuntu 24.04 LTS | не 26.04 | конфиг проверен на nginx 1.24 из состава 24.04 |
| Диск 15 ГБ | сайт занимает 98 МБ | остальное под систему, логи и запас |
| 2 vCPU, доля 20% | минимум с запасом | раздача статики процессор не нагружает |
| Фактически создано | 1 ГБ, 10 ГБ, доля 5% | меньше запрошенного, но работает; см. оговорку в конце Этапа 1 |
| Прерываемая — выкл. | обязательно | иначе машина останавливается сама |
| Статический IP | обязательно | на него смотрит A-запись домена |
